# 架构与选型逻辑

> 这份文档回答两类问题：**架构长什么样**，以及**为什么是这样**。
> 第二类更重要 —— 面试里"你用了什么"不值钱，"你在什么约束下放弃了什么"才值钱。
> 每条决策都按「背景 → 选项 → 决定 → 代价 → 什么时候该重新选」写。

## 1. 一页架构

```
┌──────────────────────────────────────────────────────────────────────────┐
│ interface/  入口层                                                        │
│   server/   FastAPI 组合根 + 6 个 router（49 条 API 路径、SSE 流式）             │
│   cli       命令行（run / search / import / export / zotero / bulk / doctor）│
│   mcp       MCP Server（把检索与格式化暴露给外部 Agent）                    │
└───────────────▲──────────────────────────────────────────────────────────┘
                │ 只向下依赖
┌───────────────┴──────────────────────────────────────────────────────────┐
│ application/  用例编排层                                                  │
│   agent/    Orchestrator + Scout / Reader / Critic / Writer / Formatter   │
│             Plan → 人工审批 → Execute → Reflect → Synthesize（可断点续跑） │
│   retrieval 混合检索与材料拼装（**不可信内容进入提示词的唯一出口**）        │
│   tools / feedback / manuscript   工具集 / 学习闭环 / 论文模块            │
└───────────────▲──────────────────────────────────────────────────────────┘
                │
┌───────────────┴──────────────────────────────────────────────────────────┐
│ infrastructure/  适配器层                                                 │
│   db/       SQLite + FTS5 + sqlite-vec；repositories/ 按业务边界拆开       │
│   api/      9 个学术数据源客户端 + Unpaywall（限流、重试、错误分类）        │
│   llm/      client / transport（重试+熔断）/ ollama+openai 后端 / json 解析 │
│   embedding/ 向量生成与增量嵌入管道（含查询向量缓存）                      │
│   importers/ RIS·BibTeX·EndNote·WoS·CSV + Zotero 只读桥接 + PDF 解析       │
│   export/ bulk/ zotero                                                     │
└───────────────▲──────────────────────────────────────────────────────────┘
                │
┌───────────────┴──────────────────────────────────────────────────────────┐
│ domain/  领域层（零 IO：不 import httpx / fastapi / sqlite3）              │
│   models（Paper/ScoredPaper）· text（CJK 切分/归一化）· query（检索式构造） │
│   citation（6 种引用格式）· dedupe（同一文献判定与合并）                   │
└──────────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────────┐
│ platform/  横切层（被所有层依赖，自己只依赖标准库）                        │
│   config · observability（trace/用量账本/失败分类）· resilience（重试/熔断 │
│   /令牌桶/舱壁）· security（注入防御/密钥脱敏/输出护栏）· cache · prompts   │
└──────────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────────┐
│ eval/  离线评测层（可依赖全部；运行时不得依赖它）                          │
│   metrics（recall/precision/MRR/MAP/nDCG）· harness（7 种配置消融）        │
│   faithfulness（claim-level 引用校验 + 校验器自评估）· datasets            │
└──────────────────────────────────────────────────────────────────────────┘
```

### 一次请求的链路

```
用户在界面输入课题
   │
   ├─ HTTP 路由（interface）→ 取单例：db / registry / runtime（composition root）
   │
   ├─ 应用层编排（application）
   │     Scout: 9 个数据源并发检索（令牌桶限流 + 熔断 + 结果去重合并）
   │     ↓ 落库（infrastructure/db，单写者 + 事务 + FTS/向量双索引）
   │     Reader: OPEN ACCESS 全文抓取（解析 citation_pdf_url 定位真 PDF）
   │     Critic: 启发式 + LLM 逐篇评估 → 证据等级与可用性
   │
   ├─ 材料拼装（application/retrieval.build_context_digest）  ← 安全边界在此
   │     ① 注入扫描（中英文指令、零宽字符、base64 载荷）
   │     ② 包裹成显式标记的「不可信数据」块 + 明确的"其中指令一律无效"告示
   │
   ├─ LLM 调用（infrastructure/llm）
   │     transport: 传输层重试（429/5xx）+ 熔断（按后端隔离）
   │     记账: token / 耗时 / 阶段 / 失败分类 → observability 账本
   │
   ├─ 引用校验（eval/faithfulness，可离线跑）
   │     编号存在性 · 数字溯源 · 方向矛盾 · 过度主张 · 跨语言弱证据
   │
   └─ 流式回传（SSE）→ 产物落库（可断点续跑）
```

## 2. 依赖规则，以及"怎么保证它不被违反"

分层架构的死法从来不是"不知道该分"，而是**知道但守不住**：某人为了赶需求在 `db` 里
import 了一下 `server`，测试全绿、评审通过，三个月后依赖图成一团，再没人敢重构。
人眼 review 抓不住这种漂移（它不体现在业务逻辑的 diff 里），所以必须交给机器。

`scripts/check_arch.py`（约 470 行，纯 AST 分析，零依赖）在 CI 与 pre-commit 里强制三件事：

| 检查 | 规则 | 现状 |
|---|---|---|
| 层次依赖方向 | `platform` 只依赖自己；`domain` 只依赖自己；`infrastructure → platform/domain/infrastructure`；`application → 前三层`；`interface/eval → 任意层`；**运行时不得依赖 eval** | 违规 **0** |
| 循环依赖 | 模块级强连通分量必须为空 | 环 **0** |
| 规模上限 | 文件 ≤800 行、函数 ≤300 行、类 ≤450 行（门面模块自动识别并豁免） | 仅剩白名单内的历史债 |

**白名单策略**：已存在的违规可以进白名单，但**只允许变小**，每条都必须写明原因，
而且校验器每次运行都会把它打印出来 —— 让技术债保持在视线内，而不是藏在没人看的 TODO 里。

### 这个校验器抓到的真实问题

1. **一条藏在函数体里的跨层 import**：`importers/__init__.py`（基础设施）为了读 PDF，
   在函数内部 `from ..agent.reader import extract_pdf_text` —— 基础设施反向依赖应用层。
   人工 review 几乎不可能发现（就是一行 import），是校验器跑出来的。
   修法不是加白名单，而是把 PDF 解析下沉到 `importers/pdf.py`（它本来就是 IO 适配器）。
2. **`db.repo ↔ embedding.pipeline` 循环依赖**：数据层在 `insert_paper(embed=True)` 里
   懒加载嵌入管道，而管道又要 import 数据层读文献。
   修法是**依赖倒置**：数据层只留一个空钩子，嵌入层在导入时注册自己
   （`register_embed_hooks`）。数据层因此完全不认识嵌入层，`embed=True` 的调用方式不变。
3. **它自己也有过一个 bug**：解析相对导入时把包的 `__init__.py` 当成普通模块，
   于是 `from .pubmed_client import ...` 被解析成不存在的 `medscholar.pubmed_client`，
   报出 27 条**假违规**。假阳性会把真问题淹没，所以解析逻辑补了测试性的核对
   （`__init__.py` 里的 `.` 指包自身；`from X import a` 的真实依赖是 `X.a` 而不是 `X`）。
4. **它不能因为被测代码有语法错误而崩掉**：实测往 `papers.py` 写进一个语法错误后，
   校验器直接抛 `SyntaxError` 打断了自己。校验器崩掉会让人怀疑校验器并绕开它 ——
   那正是架构约束失效的起点，所以现在语法错误会被降级成"该模块规模检查跳过"。

## 3. 架构决策记录（ADR）

### ADR-1 单体 Python 应用，而不是微服务

- **背景**：目标用户是**单机个人**（医学研究者/研究生），要能打包发给朋友、解压即用。
- **选项**：① 前后端分离 + 微服务；② 单体 + 内嵌前端；③ 桌面应用（Electron/Tauri）。
- **决定**：①单体 FastAPI + 免构建前端，全部依赖打包进 `.python/` 便携运行时（约 36 MB）。
- **代价**：无法水平扩展、无法多用户、部署靠"拷贝一个文件夹"。
- **何时重选**：需要多人协作或多租户时 —— 那时运行状态要落库、检索要换 Postgres+pgvector、
  长任务要进队列。

### ADR-2 SQLite（FTS5 + sqlite-vec），而不是 Postgres / 专用向量库

- **背景**：单用户、约 10³~10⁴ 篇文献量级；要求"备份 = 拷一个文件"。
- **选项**：① SQLite + FTS5 + sqlite-vec（同一文件）；② Postgres + pgvector；③ SQLite + 外部向量库（FAISS/Milvus）。
- **决定**：①。理由：**一份数据文件同时承担关系、全文、向量三种检索**，没有第二个需要备份/同步的状态；
  FTS5 的中文短板用"逐字切分 + 短语/bigram 级联"补上，不引入分词依赖；
  向量量级在 10⁴ 时暴力检索足够快（配合 `dim` 列分流）。
- **代价**：**单写者**（并发写会锁库）、没有近似最近邻索引（量大后线性扫描变慢）、
  没有真正的分区与复制。
- **何时重选**：文献量 >10⁵ 或需要多进程写入时换 Postgres+pgvector；迁移路径已铺好（见 ADR-9 的迁移框架）。

### ADR-3 免构建原生 JS，而不是 React/Vite/Next.js

- **背景**：这个应用的价值在**本地化与可分发** —— 朋友解压就能用，不该再要求 Node 工具链。
- **决定**：原生 JS 约 4.2k 行 + CSS 约 1.6k 行，三栏工作台 + SSE 流式渲染。
- **代价**：组件复用靠手写约定；`app.js` 单文件已经偏大，该拆模块了（写在技术债里）。
- **何时重选**：交互复杂度再上一个台阶（例如富文本编辑器、协同编辑）时上构建工具链。

### ADR-4 自研 Agent 编排，而不是 LangChain / LangGraph

- **背景**：流程是**固定线性 + 一个人工审批点**（Plan → 审批 → Execute → Reflect → Synthesize）。
- **决定**：自研约 600 行的编排（阶段机 + 检查点 + 断点续跑 + 事件流）。
- **理由**：框架的抽象成本在这里大于收益。我需要的四件事框架并不直接给：
  ①**阶段级检查点**（进程重启后能接续，这是被真实事故驱动的需求）；
  ②**人工审批点的持久化**；③**材料块的上下文预算逐档收缩**（本地 8B 模型只有 8192 上下文，
  要按 token 预算动态裁剪材料）；④**与自有引用编号体系强绑定**的产物校验。
- **代价**：没有框架生态（没有现成的可视化、回调、社区组件）；动态分支能力弱。
- **何时重选**：流程变成"由模型决定下一步走哪个节点"的动态图时，LangGraph 这类状态机会更划算。

### ADR-5 摘要级检索 + 全文供给写作，而不是段落级 chunk

- **背景**：综述写作需要的是"这篇文献讲什么"，引用具体数据时才需要全文段落。
- **决定**：向量与 FTS 索引建在**题录 + 摘要**上；全文单独存 `paper_fulltext` 并建独立 FTS 索引，按需取用。
- **理由**：用摘要做检索单元还能避免"同一篇文献的多个 chunk 互相竞争排名"。
- **代价**：**没有做 chunk 策略消融**，这是明确缺口。要做 claim-level 问答就必须切段落级 chunk
  并补「固定长度 / 语义边界 / 段落」的消融实验。
- **何时重选**：做"证据级问答"时。

### ADR-6 本地 Ollama 优先，云端可切换

- **背景**：医学研究者处理的**多是未发表数据**；同时本地硬件有限（RTX 4060 8GB）。
- **决定**：默认本地；统一 LLM 客户端屏蔽差异（同一套 `chat/chat_json/stream` 接口），切换只改配置。
- **实测依据**：本地 8B 模型 45~47 tok/s（**已到显存带宽天花板**：272 GB/s ÷ 6.19 GB ≈ 44 tok/s），
  模型重载一次 60~120 秒（因此默认 `keep_alive: 30m`）；云端一次综述约 2~4 万 token、成本不到一毛钱。
- **代价**：本地质量不如云端、长上下文受限；云端要出网且有隐私面。
- **产品处理**：界面上明确标注当前后端与影响，让用户自己选，而不是替他决定。

### ADR-7 印象里"应该上向量数据库"，为什么没上

见 ADR-2。一句话：**在 10⁴ 量级、单用户、要可分发的前提下，
多一个需要部署与备份的服务是净负债。** 判断依据是量级与运维成本，不是时髦度。

### ADR-8 进程内账本 + `/api/metrics`，而不是一上来接 OpenTelemetry

- **决定**：自研轻量 trace/账本（约 700 行），暴露 `/api/metrics`；失败按 11 类分类。
- **理由**：需要的是"这次综述花了多少 token/多少钱、慢在哪个阶段、哪个后端在连续失败"，
  这些用 700 行就能回答；先接 OTel 会引入采集端、后端与运维面，而当前是单机自用。
- **代价**：**账本在内存里，进程重启即丢**；没有分布式追踪、没有告警、没有持久化趋势。
- **何时重选**：要多机/多用户或需要历史趋势时，把 OTEL SDK 接到同一个 span 树上（结构已经对齐：span 有 name/attrs/children）。

### ADR-9 渐进式重构 + 兼容外壳，而不是一次性全量搬迁

- **背景**：重构时项目已有 1100 个测试、CLI/HTTP/MCP/脚本/文档都在用旧 import 路径，而且**线上库不能丢**。
- **决定**：把 `models/text/query/citation/dedupe` 搬到 `domain/`、`config` 搬到 `platform/`，
  在旧路径**留只做重导出的外壳**；god module 拆分保留稳定门面
  （`db/repo.py` 1484→157 行、`server/app.py` 1384→166 行）。
- **代价**：仓库里短期存在两套路径；外壳需要测试锁住（`tests/test_compat_shims.py` 用
  `is` 身份断言逐个核对，**漏一个私有名就会 ImportError** —— 这是实测踩到的）。
- **为什么不全量搬迁**：`db/`、`api/`、`llm/` 这些包名是公开契约，全量搬迁要 30+ 个兼容外壳文件，
  收益（视觉整齐）低于成本（风险与噪音）。所以采用
  **「新代码进新分层目录 + 旧包按映射表纳入同一套自动校验」**：分层是**被强制的**，
  不依赖目录名是否好看。

### ADR-10 主动放弃抓取订阅资源

- **背景**：用户有高校图书馆账号，很自然地会问"能不能自动下载付费论文"。
- **决定**：不做绕过付费墙、不做批量爬取订阅资源。已实现的合规路径有四条：
  题录导出导入、官方批量包（PubMed baseline / PMC OA Subset 流式导入）、
  Zotero 只读桥接、链接解析器跳转（用户自己在浏览器里完成授权访问）。
- **理由**：校外访问页面明令禁止迅雷/Flashget 之类批量下载，**处罚是永久失去校外访问权限** ——
  代价由全校承担，收益只有一个人。这条取舍在面试里是加分项，因为它证明我会算"谁承担代价"。
- **产品化处理**：分享包**断言不含 `data/`**（CI 有专门的作业），授权内容不随包分发。

## 4. 模型选型逻辑

### 4.1 生成模型（LLM）

| 候选 | 实测 | 结论 |
|---|---|---|
| 本地 `qwen3:8b` | 45~47 tok/s；中文医学表达可接受；JSON 需容错解析 | **默认**（未发表数据不出机器） |
| 本地 `qwen3.5:4b` / `qwen2.5:7b` | 更快但结构化输出更不稳 | 备选 |
| 本地 `llama3.2:3b` | **引用编号会输出字面量 `[n]` 而不是真实编号** | **不采用**（引用体系是本项目的核心，这一条是硬伤） |
| 云端 `deepseek-chat` | 质量明显更好、速度快一个数量级；推理系列要注意思维链与正文**共用 max_tokens** | 成稿质量优先时推荐 |

选型的判断标准不是"谁更强"，而是**这个场景能接受哪种失败**：医学写作里
"编号对不上"和"数字没出处"是致命失败，速度慢只是体验问题。

### 4.2 嵌入模型

| 候选 | 实测 | 结论 |
|---|---|---|
| `nomic-embed-text`（768d） | **跨语言能力弱**：同主题中英对相似度 0.3788 < 不相关中文对 0.5832 | 不推荐 |
| `bge-m3` | 多语言（中英日）+ 长文本 | **推荐** |
| `hashing`（内置确定性哈希） | 无语义，但**完全离线、确定性** | 只用于 CI 的回归门禁 |

这里有个方法论：CI 用哈希嵌入而不是真实模型，是因为"装几 GB 模型"会让 CI 又慢又脆，
一旦频繁红掉，大家就开始习惯性忽略它。CI 只做**确定性回归**（指标与融合逻辑有没有被改坏），
真实语义质量在本机用真实库测 —— 两件事混为一谈就会得出虚假结论。

### 4.3 检索策略（实测数据）

同一次消融（真实库 474 篇文献，标注查询），nDCG@10：

| 配置 | 自然语言查询 | 标题派生查询 |
|---|---|---|
| BM25（FTS5） | 0.7868 | **0.9754** |
| 纯向量 | **0.8526** | 0.8967 |
| **生产配置（RRF k=60）** | 0.8476 | 0.9815 |

**结论比"向量更好"复杂，也更有价值**：向量检索只在自然语言查询上赢（+6.6pt），
标题派生查询里 BM25 反而更强（向量 −7.9pt）。所以生产配置保留两路融合，
并在标题精确匹配场景给 FTS 更高权重。
另外做了**阴性对照**（不相关查询应返回 0 命中）与**与生产逻辑的一致性自检**
（评测用的排序函数就是生产 `hybrid_search` 用的那几个原语，`verify_production_parity` 返回空才通过）。

## 5. 一致性与并发

| 场景 | 处理 | 理由 |
|---|---|---|
| 并发写 | SQLite 单写者 + 显式事务 | 接受这个边界，换取"备份=拷一个文件" |
| 事件循环 | 检测循环变化则重建 `httpx.AsyncClient` | 连接池绑定创建它的循环，跨循环复用会**永久挂起**（实测事故） |
| 流式回传 | 异步生成器 → SSE；取消时立刻停止 | 用户点"取消"必须真的停，不能继续烧 GPU |
| 跨循环通信 | 轮询 `history`（200ms）而不是 `asyncio.Event` | `Event` 也是循环绑定的，跨循环会静默失效 |
| 阶段续跑 | 每阶段写检查点，启动时标记中断的运行 | 进程重启不该让用户白跑 20 分钟 |
| 外部 API | 令牌桶限流 + 全抖动重试 + 熔断 | 一个挂掉的源不该吃掉 1/3 的并发预算 |
| 缓存 | TTL + 容量上限 + 前缀失效；**不缓存 LLM 生成结果** | 生成结果要可重新生成、可追溯 |

## 6. 可演化性设计

- **数据库**：`schema_migrations` 版本表 + 校验和（**改了已发布的迁移会报错**，因为那会让不同机器上的库结构不同）+
  逐步事务（失败不留半成品）+ 迁移前自动备份 + dry-run。
- **提示词**：注册表带版本号与变体（A/B），占位符声明 + 渲染后校验（提示词里漏一个 `{xxx}` 会静默进入上下文）；
  默认版文本与迁移前**逐字相同**，由测试断言。
- **失败分类**：11 类（timeout / rate_limited / auth / bad_request / not_found / server_error /
  connection / parse / context_overflow / cancelled / unknown）。
  **无法分类的失败等于没有告警** —— "失败 37 次"没有信息量，"429 占 30 次"才直接指向限流。
- **缓存**：所有缓存走注册表，能一次看全、一次清干净。
- **扩展点**：新增数据源只需实现 `BaseClient` 子类并在 registry 注册；
  新增引用格式只需在 `domain/citation` 加一个纯函数；新增评测配置只需在 `harness.CONFIGS` 加一行。

## 7. 我明确不做的事

| 不做 | 理由 |
|---|---|
| 绕过付费墙 / 批量爬取订阅资源 | 代价由全校承担（见 ADR-10） |
| 把"生成得漂亮"当卖点 | 医学写作的失败代价是学术不端，重点在幻觉治理 |
| 一上来接微服务 / 向量数据库 / OTel | 单机自用阶段它们是净负债；判断依据是量级与运维成本 |
| 用没有测试守住的"约定" | 约定必须有强制手段（CI / pre-commit / 守卫脚本），否则一定会漂移 |
| 假称 Linux 已验证 | README 如实写"理论可用、未验证"，CI 里那个作业标 `continue-on-error` |
