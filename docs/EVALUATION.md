# 检索质量评测方法论

> 这份文档回答一个问题：**"检索改动让结果变好了吗？"**
> 它同时记录**这个评测不能证明什么** —— 后者同样重要。

## 为什么要有评测

在加评测之前，这个项目的检索调优是这样的：改一个参数 → 手工搜两三个课题 →
"感觉准了" → 提交。问题有三个：

1. **无法证明**。换个人来问"你怎么知道变好了"，答不上来。
2. **会调错方向**。中文检索曾经完全失效（FTS5 把整段汉字当一个 token），
   但因为没有指标，是靠用户报障才发现的。
3. **改动之间无法比较**。同时改三处，好了一点点还是坏了？不知道。

现在有了可复现的指标，每次改动都能回答"哪一项指标动了多少"。

## 指标定义

| 指标 | 定义 | 看它做什么 |
|---|---|---|
| `recall@k` | 前 k 条里命中的相关文献 / 全部相关文献 | **有没有漏**。综述场景最关键——漏掉一篇重要研究，结论就可能错 |
| `precision@k` | 前 k 条里命中的相关文献 / k | 前 k 条有多少是噪声，直接影响送进写作上下文的材料密度 |
| `MRR` | 第一个相关文献名次的倒数 | 第一条结果对不对。决定"用户看一眼能不能用" |
| `MAP` | 各相关位置上的 precision 平均 | 整体排序质量，且**漏掉相关文献会被惩罚**（分母是相关总数） |
| `nDCG@k` | DCG / IDCG，支持分级相关性 | 排序的整体质量；带位置折损，比 MAP 更贴近"用户从上往下读" |

实现都在 `medscholar/eval/metrics.py`，**每个函数都有手算用例**钉在
`tests/test_eval_metrics.py` 里。理由很简单：**错误的指标比没有指标更糟** ——
它会把优化调向错误方向，而且表面一切正常。

### 两条容易自欺的边界（都已显式处理）

1. **没有标注相关文献的查询不参与聚合**，并且单独报告 `skipped_queries`。
   把"没标注"当成 0 分会拉低均值；直接忽略又不报告，就等于用"跳过"把指标做漂亮。
   两条路都堵上：跳过 + 计数。
2. **阴性对照需要显式声明**。校验器默认拒绝"没有标注相关文献"的条目
   （那通常是漏标），但如果查询是**故意**用来观察"对无关问题会不会硬凑结果"，
   需要写 `"expect_no_relevant": true`。校验器因此能区分"忘标注"与"故意留空"。

## 两套评测，刻意分开

这是整份方法论里最重要的一条。**CI 里的确定性回归**与**本机的真实质量评测**
是两件事，混为一谈就会得出虚假结论。

| | CI 回归（`--embed-provider hashing`） | 真实质量（默认，本机 Ollama） |
|---|---|---|
| 语料 | `medscholar/eval/datasets/regression.json`，**人工合成** 40 篇 | 你本地库的真实文献（`--from-library`） |
| 嵌入 | 哈希嵌入（纯 Python，确定性、离线） | `nomic-embed-text` / `bge-m3` 等真实模型 |
| 能证明 | 指标与融合逻辑**没被改坏**；管道可复现 | 检索质量的**真实水平**与改动方向 |
| 不能证明 | 真实检索质量（哈希嵌入只反映词面重叠） | —— |
| 速度 | 秒级 | 分钟级，取决于语料规模 |

**为什么 CI 不用真实模型**：CI 环境没有 Ollama，装一个几 GB 的模型既慢又不稳定；
一旦 CI 因环境问题红掉，大家就会开始忽略它。确定性回归的价值在"稳定可用"。

**为什么真实评测不写死阈值**：绝对指标依赖具体语料与模型，写死阈值没有意义。
真实评测的用法是**看相对变化**（改前 / 改后），而不是"必须 > 0.8"。

## 评测跑的是生产代码（可执行证据）

评测框架直接调用 `search_fts` / `search_vector` / `rrf_fuse` —— 即
`hybrid_search` 内部使用的同一组原语。为了确保不会"评测一个自己重写的检索器"，
有两条测试守着：

* `test_eval_production_config_matches_hybrid_search`：断言评测的 `production`
  配置与 `hybrid_search` 的输出**逐条一致**；
* `test_parity_detects_divergence`：把 `hybrid_search` 换成倒序返回，
  断言一致性检查**能发现**（否则检查本身就是摆设）。

`scripts/eval_retrieval.py` 每次运行也会做一次同样的自检并打印结果。

## 实测结果

### A. 合成语料 + 真实嵌入（回归集 40 篇，真实 `nomic-embed-text`，@10）

| 配置 | recall@10 | nDCG@10 | MRR |
|---|---|---|---|
| bm25-only | 0.8519 | 0.8519 | 0.8519 |
| vector-only | **0.9136** | **0.8814** | **0.8695** |
| production (RRF) | 0.9136 | 0.8814 | 0.8695 |

### B. 本地库真实文献（60 篇，`title-terms` 查询）

| 配置 | recall@10 | nDCG@10 | MRR | 相对 BM25 |
|---|---|---|---|---|
| bm25-only | 1.0000 | 0.9754 | 0.9667 | — |
| vector-only | 1.0000 | 0.8967 | 0.8611 | −7.9pt nDCG |
| production (RRF) | 1.0000 | 0.9815 | 0.9750 | +0.6pt |
| weighted-fts2 | **1.0000** | **0.9877** | **0.9833** | +1.2pt |

### C. 本地库真实文献 + **自然语言查询**（25 篇，LLM 依摘要生成问题）★ 最关键

| 配置 | recall@10 | nDCG@10 | MRR | 相对 BM25 |
|---|---|---|---|---|
| bm25-only | 0.9200 | 0.7868 | 0.7440 | — |
| vector-only | **0.9600** | **0.8526** | **0.8194** | **+6.6pt nDCG** |
| production (RRF) | 0.9600 | 0.8476 | 0.8130 | +6.1pt |
| weighted-vec2 | 0.9600 | 0.8488 | 0.8143 | +6.2pt |

### 三组结果放在一起说明什么

**1. 混合检索的价值取决于查询形态，这一点只有评测能看出来。**

* 查询由**标题派生**（B）时，词面重叠高 → **BM25 更强**，向量反而拖后腿 7.9pt；
* 查询是**自然语言**（C）时 → **向量更强**，BM25 明显落后 6.6pt。

这条反差是整份评测里最有价值的发现：**"上向量检索总是更好"是错的**，
而"用标题当查询来评测"会得出完全相反的结论。如果没有 C 组，
我会基于 B 组错误地认为向量检索没用。

**2. 融合并不总是超过最好的一路。** C 组中 vector-only（0.8526）略高于
production RRF（0.8476）。差值 0.5pt 在 n=25 上属于噪声范围，**不应过度解读** ——
但它提示：当嵌入模型足够强时，BM25 一路贡献的主要是噪声，
`vector_weight` 应当调高（`weighted-vec2` 是融合配置里最好的，与此一致）。

**3. recall@10 在小语料上会饱和**，没有区分度（B 组全部 1.0）。
**语料小于一两百篇时应该看 nDCG/MRR，而不是 recall。**

**4. 中文查询仍然是明确的短板。** C 组唯一完全失败的查询是一条中文问句
（"是否可以通过调节谷氨酸释放和再摄取来治疗缺血性中风？"，recall 0.00）。
根因不在检索逻辑，而在默认嵌入模型：`nomic-embed-text` 的中英跨语言能力弱
（实测同主题中英相似度 0.3788，低于无关中文之间的 0.5832）。
→ **中文为主的场景应换 `bge-m3`**，这条已有数字支撑，不再是猜测。

### 两个"数据集本身不合格"的发现（都已固化为测试）

1. **`known-item` 模式无法区分检索配置**：查询就是标题时，BM25 在真实库上直接拿到
   recall/nDCG/MRR **全 1.0**。这个模式只能验证管道通不通，不能用来比较配置。
2. **小语料上改 `rrf_k` 完全不改变排序**：k 只对 `1/(k+rank)` 做单调缩放，
   两路排名一致时顺序不变，`rrf-k10/k60/k100` 指标完全相同。
   → 拿几十篇文献"调 k"没有意义；见 `test_rrf_k_may_not_change_order_on_tiny_corpus`。

## 阴性对照：不管问什么都给答案

回归集里有一条故意无关的查询（量子色动力学），语料里确实没有任何相关文献。
结果：**生产配置平均返回 10.0 条**（等于 top_k）。

这是一个必须显式盯住的系统特性：**RRF 融合天然总会返回 top_k**，
没有一个"我不知道"的出口。它意味着：

* 单靠检索层无法拒绝无关问题，**必须有下游兜底** ——
  这个项目里是引用越界剔除与数字溯源校验；
* 也说明"相关性阈值"（`retrieval.min_score`）是一个值得调的旋钮，
  但调它需要在真实语料上看召回与噪声的取舍。

这类"系统会犯错，我要知道它怎么错"的观察，比一个漂亮的均值有用得多。

## 消融实验：每一路各贡献多少

`CONFIGS` 定义了 7 种配置：`bm25-only` / `vector-only` / `production(RRF k=60)` /
`rrf-k10` / `rrf-k100` / `weighted-fts2` / `weighted-vec2`。
报告会给出完整对比表与**相对基线的差值**，所以"加了向量检索到底有没有用"
是一个可以当场回答的问题，而不是信念问题。

## 引用支持性（claim-level faithfulness）

检索级评测只能证明"文献**被检到了**"，不能证明"`[n]` **支持**那句话"。
"结论被说反了"这类错误能通过引用存在性校验，却是医学写作里最严重的错误之一。

```bat
:: 核查数据库里最新的那份综述
.python\python.exe scripts\eval_faithfulness.py --from-db
:: 跑完整版（含 LLM 逐条判定）
.python\python.exe scripts\eval_faithfulness.py --from-db --llm
:: 评估校验器本身
.python\python.exe scripts\eval_faithfulness.py --labels
```

### 分层设计

蕴含判断（entailment）不是正则能做的事，所以这里**不假装**一步到位，而是分两层，
报告中永远分开呈现：

**Tier 0 — 确定性规则**（无模型、离线、CI 可跑）

| 规则 | 抓什么 | 严重度 |
|---|---|---|
| `existence` | 编号不存在（越界引用兜底） | high |
| `numbers` | 论断里的数字在**被引文献里找不到**（编造数据的强信号） | high |
| `direction` | 论断说"显著优于/治愈"，而被引文献明确写"无显著差异" | high |
| `overclaim` | "证实/治愈/彻底"配弱证据载体（protocol / preprint / 病例报告） | medium |
| `grounding` | 同语言下实词重合度极低（可能引错文献） | medium |
| `cross_lingual` | 跨语言且**无任何语言无关信号** → 放弃判断 | low |
| `script_independent_only` | 跨语言但数字/术语/缩写对上了 → 弱证据通过 | low |

**Tier 1 — LLM 裁判**（`--llm`，可选）：逐条给
`supported / partial / unsupported / contradicted` + 理由 + 原文证据片段；
支持 `--self-consistency`（问两次，不一致标 `uncertain`）。

### 被真实数据推翻的那个决定（值得单独讲）

最初的设计是：**跨语言引用一律 abstain**（因为词面代理在跨语言对上没有信号，
指控它"引错了文献"是误报）。逻辑上没错，但一跑真实数据就崩了：

> 你库里那份真实综述（中文）21 条带引用论断里，**17 条落进 `unverifiable`** ——
> 因为中文综述引英文文献**本来就是常态**。一个对主要场景全部弃权的校验器，
> 等于没有校验器。

修法是：**语言无关信号是跨语言场景下唯一可用的证据**。
数字、术语、缩写（rTMS / PSD / HAMD / DLPFC / PEDro）不随语言变化。
把它们用起来之后，同一份综述的 21 条论断全部得到核对（`weakly_supported`），
并且能**抓错**——若论断里的缩写不在被引文献中出现，仍然会被指控。

修复后 CLI 在真实综述上的输出：

```
带引用的论断    : 21 条
引用覆盖面      : 30%
— 判定分布 —
  weakly_supported   21          ← 全部只靠语言无关信号核对通过
— 规则命中 —
  script_independent_only   21
说明：跨语言引用：21 条仅凭语言无关信号（数字/术语/缩写）核对通过，
      0 条因无任何共同信号而无法核实。这类论断的语义支持性需要 Tier 1。
```

注意 `weakly_supported` 这个档是**特意单列**的：报成 `supported` 会让人误以为
"语义已核实"，报成 `unverifiable` 又等于对主要场景弃权。单列一档最诚实。

### 校验器本身准不准（evaluate the evaluator）

一个从没被衡量过的校验器，可信度和"没有校验器"差不多。所以在人工标注集
（`datasets/faithfulness.json`，27 条边界清晰的构造案例）上衡量它：

| 指标 | 结果 |
|---|---|
| 判定完全一致 | **24/27 = 88.9%** |
| 预期规则命中 | **20/20** |
| **二分类 recall** | **1.00**（零漏报 —— 标注集里所有真问题都抓到了） |
| 二分类 precision | 0.89 |
| 二分类 accuracy | 0.93 |
| `contradicted` | **P=1.00 R=1.00**（方向矛盾全抓、无误报） |
| `unverifiable` | P=1.00 R=1.00 |

**门禁规则**：召回必须 1.0（漏报一个"结论被说反了"可能直接进论文），
精确率下限 0.85（允许语义改写导致的误报）。已接进 CI 的 `eval` 作业。

**这个自评估真的抓到过 bug**，这也是它存在的意义：

1. **CJK 分词错误导致中文规则静默失效**：`[\u4e00-\u9fff]{2,}` 会把整句汉字
   贪婪匹配成一个 token，于是中文论断与任何来源的重合度恒为 0 ——
   全部中文矛盾案例漏报。这与本项目在 SQLite FTS5 上踩过的是**同一个坑**。
2. **跨语言误报**：修好分词后反向爆炸，每条中文论断都被判"引错文献"。
3. **同一逻辑重复实现**：`_content_words` 与 `_lexical_profile` 分头维护，
   修了一个漏了另一个 —— 已合并为单一事实来源。

### 已知盲区（刻意保留在标注集里度量，而不是藏起来）

| 盲区 | 表现 | 为什么保留 |
|---|---|---|
| **语义改写** | 同语言但用上位词改写（"神经调控手段/情绪障碍" vs "重复经颅磁刺激/抑郁症状"），实词几乎不重合 → 误报 `unsupported` | 这是**词面代理指标的固有局限**，保留 2 条案例持续度量误报率，也说明为什么需要 Tier 1 |
| **跨语言无语义信号** | 纯中文论断 vs 纯英文文献且无共同术语 → abstain（漏报） | 有意接受的漏报：反过来做会把每一条跨语言引用都冤枉成引错文献 |
| **多规则命中时的仲裁** | 一条论断同时触发 numbers + overclaim + grounding 时只报最严重的一个 | 仲裁顺序是明确写出的设计决定，不是掩盖漏报 |
| **不是人类一致率** | 标注集由本项目作者编写、条目边界清晰 | 它证明"规则在无歧义案例上可靠"，**不能**声称达到人类水平 |

### 接进产品

`--from-db` 直接从数据库取产物与它的引用映射（编号 → 文献，用产物 meta 里的
`references`），因此核查的是**真实生成结果**，不是另写的测试样例。
`--llm` 打开 Tier 1；**中文综述引英文文献的场景建议开启** ——
Tier 0 在那种情况下只能给弱证据结论。

## 怎么用

```bat
:: 1) CI 同款：确定性回归 + 阈值门禁（秒级，不需要 Ollama）
.python\python.exe scripts\eval_retrieval.py --dataset regression --k 10 --embed-provider hashing --check

:: 2) 本机真实评测：在你自己的库上跑（需要 Ollama）
.python\python.exe scripts\eval_retrieval.py --from-library --limit 60 --k 10

:: 3) 只跑某几个配置做对比
.python\python.exe scripts\eval_retrieval.py --config bm25-only --config production --k 10

:: 4) 导出完整报告（含逐查询明细）供分析
.python\python.exe scripts\eval_retrieval.py --dataset regression --json .cache/report.json
```

### 构造你自己的黄金数据集

```bat
:: 从本地库生成候选（三种模式，偏差从大到小：known-item / title-terms / llm-question）
.python\python.exe scripts\build_golden.py --mode llm-question --limit 60 --out eval/draft
```

生成后**必须人工过一遍**：删掉有歧义的条目、确认 `relevant` 正确、
把确认过的 `source` 改成 `manual`。自动生成的查询一定有偏差，
直接把自动结果当基准就是自欺——脚本把体力活做掉，但保留人的判断权。

## 门禁阈值怎么定

阈值在 `scripts/eval_retrieval.py` 的 `DEFAULT_THRESHOLDS`，按**确定性模式**的
实测基线标定并留约 8~10% headroom：

| 指标 | 基线（production，hashing） | 下限 |
|---|---|---|
| recall@10 | 0.8889 | 0.80 |
| nDCG@10 | 0.8678 | 0.78 |
| MRR | 0.8611 | 0.77 |

**定得太紧的门禁比没有门禁更糟**：它会频繁误报，然后所有人都会开始习惯性忽略它。
门禁的职责是抓"把检索改坏了"，不是抓"没达到理想水平"。

## 这个评测目前**不能**证明什么

诚实列出边界，避免过度解读：

1. **没有 claim-level 忠实度**：现在的"引用"相关指标只到"文献是否被检索到"这一层。
   `[n]` 是否真的支持那句话，需要 NLI 模型或 LLM 逐句核验 —— 尚未实现。
2. **合成语料的绝对值无意义**：回归集只有 40 篇人工合成条目，指标只能用于**相对比较**。
3. **`known-item` 模式高估 BM25**：查询就是标题时词面重叠极大。
   所以 `--from-library` 的报告里按 `source` 分组展示，就是为了让这个偏差**显形**。
4. **只有单轮检索**：没有评估多跳检索、查询改写、重排（这些还没实现）。
5. **语料是题录+摘要，不是全文**：与生产的检索索引口径一致（这是有意的），
   但如果将来改成段落级 chunk，评测集与指标都要跟着重做。
