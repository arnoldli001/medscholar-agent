## 1. 主推案例：一个"AI 一次写成的一对函数"，让主力文献源静默归零

> **这个案例最推荐讲**：根因清晰、证据链完整（本地 + 真实 API 双证据）、
> 有反直觉的"测试全绿却错了"的转折、还能自然过渡到方法论。

### 1.1 问题（现象）

核对真实运行日志时，我发现一个数字异常：

| 数据源 | 成功请求数 | 累计命中 |
|---|---|---|
| pubmed | 8 | 62 条 |
| openalex | 6 | 180 条 |
| crossref | 8 | 240 条 |
| **europepmc** | **7** | **0 条** |

**Europe PMC 有 7 次"成功"请求，命中 0 条。** 注意：`error` 字段是 `NULL`（成功），
不是报错。而 Europe PMC 恰好是这个项目 OA 全文的主力来源。

### 1.2 排查（这段最能体现方法）

我拿生产数据库里 **plan 阶段真实产出的 4 条检索式**（不是我构造的测试用例），
直接跑翻译函数：

```
输入：rTMS AND post-stroke depression AND (HAMD OR MADRS) AND (randomized OR RCT)
输出：(rTMS AND AND AND "post-stroke" AND depression AND ((HAMD OR MADRS)) AND ((randomized OR RCT)))
              ↑↑↑↑↑↑↑↑
```

**4 条真实检索式，4 条全部畸形。**

再打真实 API 确认后果：

| 发给 Europe PMC 的 query | HTTP | hitCount |
|---|---|---|
| 客户端构造的表达式 | 200 | **0** |
| 去掉 `AND AND` 后的同一表达式 | 200 | **157** |

### 1.3 根因（**这是整个案例的核心洞察**）

`domain/query.py` 里有一对方向相反的函数，是**同一次 AI 生成**写出来的：

```python
# 解析器：接受的运算符词表
_OR_WORDS  = {"or", "或者", "｜"}        # 有 OR
_NOT_WORDS = {"not", "-", "排除", "非"}  # 有 NOT
#                                          ← 没有 AND

# 序列化器：发出的运算符词表
expression = " AND ".join(units)         # 用 AND 拼接
```

**序列化器发出的词表，严格大于解析器接受的词表。**

于是 `AND` 作为普通词落进 `must` 列表，序列化时再拼一层 `" AND "`，
产生 `AND AND`。

**更关键的深层原因**：这个模块的 docstring 写的是

> 「空格与逗号 = AND、`|` 或 `OR` = 任选、`-` 或 `NOT` = 排除」

**文档的词表本身就是解析器词表的子集** —— 实现忠实于文档，文档忠实于
"用户会怎么写"，但**漏掉了"上游实际会发来什么"**：这里的上游是一个被要求
"写 PubMed 风格检索式"的 LLM，它必然用标准 PubMed 语法，也就是**显式的 `AND`、
分组括号、以及同义词 `OR` 组**。

### 1.4 为什么 1384 个测试全绿却漏了（**面试官最想听的一段**）

三个原因叠加，每个都值得单独说：

**① 测试用例的复杂度低于真实输入的复杂度**

旧测试用的查询是：

```python
{"query": "rTMS AND depression"}     # 无 OR 组、无括号
```

它恰好**不触发** `AND AND`——因为只有一个 `AND`，被吃进 must 后拼出来仍然"像模像样"。
而生产里 LLM 输出**必然带 OR 组**（同义词）和括号（PICO 分层），畸形必然出现。

**② 测试按函数组织，接缝处没有归属**

测试树的结构 = 代码结构。`test_query.py` 有 `test_space_is_and`（空格=AND）、
`test_pipe_is_or`、`test_explicit_or_word` —— 覆盖了隐式 AND 和 OR，
**但没有一条测试跨越"解析器 ↔ 序列化器"这条缝**。

**③ 失败是静默的**

Europe PMC 对语法错误的表达式返回 **HTTP 200 + hitCount=0**，不是 4xx。
所以失败分类器判它"成功"、检索日志记 `error=NULL`、前端显示
"Europe PMC 检索完成，0 条 —— 用户以为这个库就是没有相关文献"。

> **唯一能看出异常的是"0 条"这个数字本身，而它和"真的没有"长得一模一样。**

### 1.5 修完之后：同一根因**又复发了两次**

这是本案例最值钱的部分 —— 它把"修一个 bug"升级成"识别一个缺陷族"。

修完 `AND` 后，我用"往返性质"（`parse(serialize(x)) ≡ x`）复查，发现同一个根因
还有两个未爆的雷：

| 复发 | 现象 | 危害等级 |
|---|---|---|
| **分组括号当检索词** | `(meta-analysis OR systematic review)` → `must` 里出现 `'review)'`、`any` 里出现 `'(meta-analysis'`；`(rTMS OR …)` 甚至解析出 `must=[')']`，翻译时产生**空组 `()`** | 高（检索词字面带括号，永远搜不到） |
| **`ANDNOT` 被当普通分隔符** | `rTMS ANDNOT 动物`（arxiv 的排除语法）→ `must=['rTMS','ANDNOT','动物']` | **最高：语义反转** —— "排除动物"变成"必须包含动物"，且无任何错误信号 |

**语义反转比"搜不到"严重得多**：前者是结果错误，后者只是结果少。

### 1.6 而且——**我写的守卫也漏了一次**（诚实边界，主动讲）

修 `AND` 时我加了一道"输出合法性自检"，用来防止畸形表达式再被发出去。
但它只查了双运算符：

```python
for bad in ("AND AND", "OR OR", "NOT NOT", ...):   # 只枚举了"具体串"
    if bad in expression:
        raise AssertionError(...)
```

**漏了空组 `()`** —— 于是括号缺陷顺利穿过这道自检发到上游。
**守卫和它要守护的代码犯了同一个错**：词表覆盖不全。

修法是**按位置枚举**而不是按具体串枚举：

```python
_OP = r"(?:AND|OR|NOT|ANDNOT)"
BAD_POSITIONS = (
    rf"^\s*\(*\s*{_OP}\b",     # 以连接符开头
    rf"\b{_OP}\s*\)*\s*$",     # 以连接符结尾
    rf"\(\s*{_OP}\b",          # 紧跟左括号
    rf"\b{_OP}\s*\)",          # 紧贴右括号
    rf"\b{_OP}\s+{_OP}\b",     # 两个连接符相连
)
```

顺带发现守卫第一版还会**误报**：它把 `(HAMD OR MADRS)` 里合法的中缀 `OR` 也拦了。
所以「守卫本身也要有测试」——喂畸形输入断言抛错，喂合法输入断言**不**抛错。

### 1.7 结果

- 修复后 4 条真实检索式在 Europe PMC 从 hitCount=0 变为 **157 / 293 / 271** 量级（真实 API 实测）
- 数据源命中率 **3/5 → 5/5**；修一个解析器缺陷**同时修好了检索召回和 OA 全文获取两条链路**
- 新增 23 条回归测试，按**往返性质**参数化（4 条真实查询 × 4 个数据源 = 16 个组合），
  而不是只钉住那一条查询
- 归纳出 skill `interface-vocabulary-parity`：三条可机械检查的性质，让它不可能再犯

### 1.8 面试官会追问什么

| 追问 | 怎么答 |
|---|---|
| **"AI 写的代码你怎么保证质量？"** | 「我不假设 AI 写的东西是对的，我假设**接缝处一定会错**。AI 很擅长把一个函数写对，但一次生成里写完两侧时，它保证不了两个函数之间的性质。所以我的动作是固定的：写完一对相反方向的函数，立刻做**词表差集**——序列化器发出的记号集合减去解析器接受的记号集合，不为空的每一项都是一个潜在缺陷。这次的 `AND`、括号、`ANDNOT` 三个都是这么找出来的。」 |
| **"为什么测试没抓住？"** | 三层：① 测试用例复杂度低于真实输入（旧用例无 OR 组无括号，恰好不触发）；② 测试按函数组织，接缝处没有归属；③ 失败静默（HTTP 200 + 空结果，错误不回流）。**根因是"最终产物"没有验收测试，只有"函数"有。** |
| **"你为什么想到查这个？"** | 「我在核对真实运行日志时对每一列数字问了一句'这个数合理吗'。Europe PMC 7 次成功请求命中 0 条——这不是'没找到'的样子，这是'查询根本没生效'的样子。**只看报错会漏掉全部静默失效。**」 |
| **"怎么防止再犯？"** | 「不是'记住 AND 要识别'，而是把它变成性质：往返一致、守卫按位置枚举、测试输入复杂度不低于真实输入。这三条写进了 skill，任何 AI 下次写这类成对函数时会先加载它。」 |
| **"语义反转那个你怎么发现的？"** | 「修完 `AND` 我没停手，用往返性质把**全部**目标端跑了一遍（7 个数据源）。`arxiv` 的序列化用 `ANDNOT`，而解析器不认识它——`-动物`（排除）往返后变成 `must=['ANDNOT','动物']`（必须包含）。**方向反了，而且没有任何错误信号。**」 |
| **"你自己有没有犯错？"** | 主动讲 1.6：守卫漏了空组、还误报过合法中缀运算符。「**守卫是代码，也会写错。**所以我现在给守卫也写测试：畸形输入必须抛错，合法输入必须不抛错。这次两个方向都栽过。」 |

## 2. 第二个案例：成稿的引用编号和参考文献表**全部**对不上

> 与案例 1 互补：案例 1 是"接口词表"，这个是"数据在流水线里被重新编号"。

### 2.1 问题

抽检两份真实产物：

| 产物 | 正文引用编号 | 参考文献表编号 | 越界引用 |
|---|---|---|---|
| artifact 1 | 1,2,3,5,7,9,10,11,12,14,16,17,21,22,24 | 1..15 | **16,17,21,22,24** |
| artifact 2 | 2,4,7,12,13,16,19,20 | 1..8 | **12,13,16,19,20** |

正文写 `[16]`，参考文献表里没有第 16 条——`[16]` 实际是表的第 1 条。
**每一篇综述的每一条引用都指向错误的文献。** 在医学场景，这不是 bug，是学术不端风险——
而这恰好是这个项目声称要解决的问题。

### 2.2 根因

`AgentState.citation_map` 是 `{编号: Paper}`，编号是**唯一真相源**。
但成稿阶段为了"只输出被引用过的条目"，把 entries 过滤成 `[Paper]`，**丢掉了 index**：

```python
# 过滤时把 index 消费掉了
kept = [paper for index, paper in entries if index in cited]   # ← index 丢了
format_reference_list(papers, style)
  └─ for i, paper in enumerate(items, start=1):                 # ← 从 1 重新编号
```

于是正文用一套编号（1..25 带空洞），参考文献表用另一套（1..15 连续）。

### 2.3 为什么两道运行时校验都没拦住

1. `selfcheck(state.draft, entries)` 拿的是**未被过滤**的 `citation_map`
   （编号与正文一致，所以"通过"）
2. `validate_citations` 比较的也是内部一致的变量

**没有任何一处校验"成稿"这个最终字节串。**

### 2.4 修法与结果

- 让编号有唯一真相源：`format_reference_list` 增加 `indices` 参数，
  `build_references` 显式传递原始编号；导出器同样处理
- 补**端到端断言**：`正文编号集合 ⊆ 参考文献表编号集合`
- 顺带修掉一个被掩盖的假告警：LLM 自审报"参考文献表中有 **17 条**未被正文引用"——
  这个 17 是编号错位的产物，不是真实问题

**这个案例的方法论收获**：「**测试测的是组件，不是产物**」。
1384 个测试全绿是因为断言定在"标题在不在"而不是"编号对不对"，
且两道运行时校验都在看中间变量。**修法的重点不是改代码，是加一条对最终产物的验收断言。**

## 3. 第三个案例：预取了 197 万字符全文，写作阶段一字未用

### 3.1 问题

配置里有 `warm_fulltext: true`，注释写"为开放获取文献预取全文，写作质量更高"。
但审计发现写作阶段的材料块**只包含标题和摘要**。

两步取证：

**静态追数据流**：`digest_papers` 的签名里**没有全文参数**，
无论 `paper_fulltext` 表里存了多少，`max_abstract=800` 就是天花板。

**对最终产做逐字比对**：成稿正文与库里所有全文做 60 字滑动窗口匹配——

```
库内 82 篇全文 / 1,967,575 字符
成稿与之逐字重合（60 字窗口）：0 篇
```

**197 万字符的全文，零引用。**

### 3.2 影响

预取全文的完整成本链（网络下载 + PDF/JATS 解析 + 落库 + 建 FTS 索引）
**消费方是零**。而 `fulltext_top_n` 这个旋钮调大调小，对产出没有任何影响。

### 3.3 我做的决策与理由（**架构师岗最想看这段**）

**决策：接上全文，而不是摘掉预取链路。** 四条理由：

1. **速读笔记已消费全文** —— 摘除会让"单篇速读"退化为只用摘要，质量明显下降
2. **存储成本已付出** —— 82 篇 / 197 万字符已在库里；让它在主链路上有产出，
   ROI 远高于摘除
3. **`fulltext_fts` 索引已建** —— 接上不引入新基础设施
4. **`fulltext_top_n=4` 是纯浪费旋钮** —— 要么让它生效，要么删掉；
   配置文件里每一个旋钮都是对用户的承诺

**修的时候发现一个安全边界**：全文是**更高危的注入面**。
摘要经过数据源结构化（多数字段被引用方编辑过），而全文是出版商原始内容——
任何人在已抓到的 PDF 上加一段隐写指令就能污染后续综述。
所以接入时**必须同步把全文纳入 `detect_injection` 扫描**（原实现只扫 title+abstract）。

**并且成本要可控**：全文按预算注入，且只在最终 `select_papers` 之后按需注入——
避免"预取 25 篇但只用 8 篇"的新浪费。

## 4. 我做的其他判断（挑几个能在追问时加分的）

### 4.1 "实现了但没接线"是一类跨模块缺陷

审计时做了一次"抽象是否有调用者"的扫描：

| 抽象 | 实现质量 | 生产调用者 |
|---|---|---|
| `TraceRecorder` / `create_trace` | 高（contextvars 隔离并发、嵌套成树） | **0 个** |
| `Bulkhead`（并发舱壁） | 高（同步/异步双路径、peak 统计） | **0 个** |
| `add_citations` | 完整 | **0 个** → `get_references` 恒返回空 |

**这些抽象的单元测试都是绿的**——它们各自逻辑正确。缺陷不在实现，在**接线**。

后果是**跨模块的、单模块测试永远发现不了的**：`_record` 记账时尝试从上下文
推断阶段，但没人创建 trace，于是 `phase` 与 `run_id` **恒为空串** →
`/api/metrics` 的 `by_phase` 分组**永远只有一个桶"未标注"**——
项目投入实现的"按阶段聚合成本"能力，在真实运行中完全不可用。

**面试可讲的一句**：「覆盖率度量'被执行'，不度量'被使用'。
`Bulkhead` 的每行都被测试覆盖过，但它没有被生产调用过。」

### 4.2 一个我自己差点栽进去的坑（讲出来是加分项）

修 trace 时，我需要在工作流入口包一层 `with trace.span(...)`。
第一次的做法是"在已闭合的 try 块外层加一行"——看起来只多一行，
但 Python 用缩进表达所有块，**只多外层一行 = 内层几十行全部要重缩进**。
我漏了一行，结果 `else:` 浮在 `if` 之外：

```
SyntaxError: invalid syntax（pytest 收集阶段）
→ 1384 个测试全部无法运行
```

**修法**：改用**装饰器**。

```python
@_traced_phase("plan")
async def plan(self, state, *, emit=None, feedback=""): ...
```

每个方法 1 行改动、**零缩进风险**；无 trace 时（CLI/脚本/测试）零开销直通。

**方法论**：任何"同时影响 5 行以上缩进"的改动，先在本地跑
`pytest --collect-only` 再跑全量——collect-only 是语法错误的"快速触电测试"。

### 4.3 一个"优化"本身也有脆弱性（主动暴露边界）

为了在无人建 trace 时也能拿到阶段名，我在记账函数里加了**调用栈推断**兜底。
第一版用固定层数：

```python
for _ in range(8):
    frame = frame.f_back     # ← 深调用栈越界、浅调用栈停在后端内部
```

结果在深调用栈下走过头（返回 None），浅调用栈下停在 `llm/` 内部。
改成**按文件路径找第一个"业务帧"**（在 `medscholar/` 内且不在 `llm/` 内），
并给推断值加 `inferred:` 前缀，让下游一眼看出这不是真实 trace 上下文。

**面试可讲**：「fallback 机制必须有明确的'我是猜的'标记，
否则三个月后没人知道这个值是推断的还是真实的。」

### 4.4 成本工程：一个 10 行改动省 30% 成本

**发现**：section 提示词的拼接顺序是「课题 → 章节标题 → 要点 → **材料块** → 字数要求」。
5 个章节的请求在第 3 段就分叉，**云端前缀缓存命中率 0**。

**修法**：把 5 章节共用的材料块挪到最前面：

```
[系统提示词（固定）] + [材料块（5 节完全相同）] + [字数要求（固定）] + [章节标题+要点（唯一变化）]
```

后 4 个章节的输入全部命中缓存（DeepSeek 缓存命中价约为标准价 10%）。
**零质量代价的成本优化** —— 优先于"换小模型""少看几篇"这类降规格手段。

### 4.5 检索质量：FTS「逐级放宽」的短路把宽召回整条丢掉

`search_fts` 实现了一个三级降级级联（phrase → bigram-AND → bigram-OR），
但写法是"任一级命中就返回"：

实测 28 条查询：phrase 候选 15 条、bigram-AND **也是 15 条**（从未多召回任何一条）、
bigram-OR 有 **760 条**但仅在前两级都空时才启用。

**只要 phrase 命中 1 篇，就放弃了本来能召回 30~39 篇的那条路径。**
改成并集后交给 RRF 融合真正排序。

## 8. 三条主线（任何问题都往这上面靠）

1. **静默失效治理** —— 不报错、日志正常、测试全绿，但产出是错的。
   这类缺陷只能靠"对最终产物做断言"+"对每个数字问一句合理吗"来发现。
2. **接缝处优先** —— AI 擅长写对单个函数，不擅长保证两个函数之间的性质。
   所以审计资源优先投在**跨模块的接缝**上（解析↔序列化、产出↔引用表、抽象↔接线）。
3. **把发现升级成守卫** —— 修一处算一处是初级；把它归纳成可机械检查的性质，
   并固化成机器守卫（CI 门禁 / 回归测试 / skill），才是资深。
